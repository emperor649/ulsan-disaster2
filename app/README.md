# 기상재난알림 (WeatherDisasterAlert)

기상청 기상특보 + 실측 강수량 + 행정안전부 재난 위기경보(재난문자)를 연계해
지역별 실시간 위험도를 산출하고 푸시 알림으로 통보하는 Android 앱.

## 프로젝트 구조
```
app/src/main/java/com/ulsan/disasteralert/
├── data/            위험도 모델 + RiskCalculator (핵심 로직)
├── network/         기상청/행안부 공공데이터 Retrofit API
├── worker/          WorkManager 주기적 폴링(15분) + 부팅 재등록
├── notification/    알림 채널, FCM 긴급 푸시 수신
├── ui/              메인화면(지역 리스트), 지역등록, 상세화면
└── util/            관심 지역 로컬 저장
```

## 시작하기 전 필요한 것
1. **Android Studio** (최신 버전) 설치
2. **공공데이터포털**(data.go.kr) 가입 후 아래 API 활용신청
   - 기상청_단기예보 조회서비스 (기상특보, 초단기실황)
   - 행정안전부_재난문자 발송현황 (safetydata.go.kr 별도 가입 필요할 수 있음)
3. **Firebase 프로젝트** 생성 → `google-services.json`을 `app/` 폴더에 추가
   (긴급 위기경보를 폴링 주기(15분)보다 빠르게 push하려면 필수)
4. `local.properties.example`을 참고해 `local.properties`에 발급받은 서비스키 추가

## 다음 개발 단계 (우선순위 순)
1. **격자좌표 변환**: 기상청은 위경도가 아닌 격자(nx, ny) 좌표를 사용합니다.
   기상청이 제공하는 "위경도-격자 변환 프로그램"을 `util/GridConverter.kt`로 포팅해서
   지역 등록 시 주소만 입력하면 자동 변환되게 해야 합니다. (현재는 수동 입력)
2. **서버(백엔드) 구축**: 현재는 클라이언트가 직접 공공API를 호출하는 구조입니다.
   실서비스에서는 서버가 모든 사용자를 대신해 주기적으로 API를 폴링하고,
   변화 감지 시 FCM으로 push하는 구조로 바꾸는 것을 강력히 권장합니다
   (공공데이터 API는 트래픽 제한이 있어 사용자 단말이 직접 호출하면 금방 초과됩니다).
3. **Room DB 도입**: 현재 SharedPreferences로 되어있는 지역 저장소와,
   위험도 이력을 Room으로 전환해 추이 그래프/오프라인 조회를 지원.
4. **응답 파싱 정교화**: 기상특보 코드(`warnVar`, `warnStress`)와 재난문자 필드는
   실제 발급받은 API 명세서의 정확한 코드표를 반영해 매핑 로직을 다시 확인해야 합니다.
5. **위치 자동 감지**: `play-services-location`은 이미 의존성에 포함되어 있으니
   GPS 기반으로 현재 위치의 관할 특보구역을 자동 매핑하는 기능 추가.
6. **테스트 & 배포**: Play Console 등록, 서명 키 생성, 개인정보처리방침(위치정보 수집 고지 필수).

## 알림 정책
- WorkManager가 15분마다 폴링하며 위험도가 SAFE 이상이면 로컬 알림 발송
- 서버 측에서 긴급 감지 시 FCM data message로 즉시 push (DisasterFcmService)
- DANGER/SEVERE 단계는 긴급 채널(소리+진동), CAUTION/WARNING은 일반 채널로 분리

## 과거 이력 연계 종합 위험도 판단 (v0.2)

단순히 "현재 비가 얼마나 오는가"가 아니라 **"이 지역에서 이 정도 비가 왔을 때 과거에 무슨 일이 있었는가"**를
기준으로 판단하는 구조를 추가했습니다.

### 왜 이 방식인가
같은 100mm 비라도 지역마다 피해 발생 여부가 다릅니다. 배수 능력, 지형, 하천 근접도가 다르기 때문입니다.
과거에 더 적은 비에도 피해가 났던 지역은 그만큼 임계값이 낮다는 뜻이므로, 이를 역산해 보정 계수로 씁니다.

### 계산 구조
```
최종 위험도 = (실시간 기본점수 × 지역 취약계수 × 만조계수) + 상습침수지 임박 가산 + 과거사례 유사도 가산
```

- **지역 취약계수** (`VulnerabilityAnalyzer`): 과거 최저 피해 발생 강수량, 상습 침수지 밀도,
  인명피해 직결 지점 수, 재해 발생 빈도에서 역산 (1.0 ~ 2.0 배)
- **만조계수**: 차바(2016) 당시 울산 피해가 커진 결정적 원인이 만조와 겹쳐 배수가 막힌 것이었습니다.
  중구·남구·동구 등 하구 지역은 만조와 겹칠 때 1.35배 가중
- **상습침수지 임박 가산**: 각 지점별 침수 임계값의 80% 도달 시부터 가산 시작
- **과거사례 유사도**: "차바 때의 62% 수준" 형태로 진행률 산출

### 반영된 실제 데이터 (`UlsanHistoricalData.kt`)
| 사례 | 최대 시간당 | 총 강수량 | 비고 |
|---|---|---|---|
| 태풍 차바 (2016.10.5) | 104.2mm | 266mm (북구 매곡동 370mm) | 만조 겹침, 피해액 1,930억 |
| 2025년 7월 호우 | 58.5mm | 332mm (울주 두서면 3일) | 태화강 홍수경보, 산사태 심각 |
| 2025년 8월 호우 | 40mm | 113.8mm | 우정동 지하차도 침수 |
| 2024년 8월 호우 | 35mm | 90mm | 온산 원산리 차량 침수 |
| 2026년 8월 호우 | 30mm | 145.3mm | 교동 담벼락 붕괴 |

상습 침수지 18개소를 구·군별로 등록했으며, 각 지점마다 과거 침수가 시작된 강수량을 임계값으로 두었습니다.
지하차도(우정동·상방)는 인명피해 직결 지점으로 최우선 가중치를 부여했습니다.

### 알림이 달라지는 점
기존: `[경고] 중구 호우주의보 · 시간당 45mm`

개선: 
```
[위험] 중구 위험도 14점
호우경보 · 시간당 45mm
▶ 태풍 차바(2016.10.05) 당시의 43% 수준입니다. 태화강 범람, 주택침수 2,968건...
▶ 임박 지점:
  · 우정동 지하차도 (128%)
  · 태화종합시장 일원 (112%)
▶ 위험 단계입니다. 상습 침수지 사전 통제와 취약계층 연락을 시작하세요
▶ [우정동 지하차도] 즉시 진입 차단 필요 — 지하차도 침수는 인명피해로 직결됩니다
```

### 데이터 검증이 필요한 부분 (중요)
현재 시드 데이터는 언론 보도와 기상청 발표자료를 정리한 값이라 **정밀도에 한계가 있습니다.**
실서비스 전에 아래 원본 통계로 교체·검증하세요.

1. **행정안전부 재해연보** — 연도별·시군구별 피해 원인과 금액 공식 통계
2. **국가재난관리정보시스템(NDMS)** — 개별 피해 신고 건별 위치 데이터 (지자체 협조 필요)
3. **울산시 자연재해저감 종합계획** — 법정 계획으로 침수위험지구가 이미 지정·고시되어 있습니다.
   이 문서의 지정 구역이 현재 하드코딩한 hotspot 목록보다 훨씬 정확합니다.
4. **국립해양조사원 조위관측소 API** — `TideChecker`가 지금은 빈 구현입니다.
   울산 조위관측소 실측/예측값으로 반드시 채워야 만조 계수가 작동합니다.
5. **홍수위 데이터** — 한강홍수통제소 API로 태화강 사연교·태화교, 동천 병영교 실시간 수위 연계
   (2025년 7월에 실제로 홍수경보가 발령된 지점들입니다)

### 다음 단계

- 하천 수위 API 연계 — 강수량보다 직접적인 침수 예측 지표

## 하천 수위 연계 (v0.3)

강수량은 **간접 지표**입니다. 실제로 사람이 다치고 차가 잠기는 건 물이 넘칠 때고,
그건 하천 수위가 직접 알려줍니다. 그래서 홍수통제소 수위 API를 붙였습니다.

### 왜 "현재 수위"가 아니라 "상승 속도"인가
차바 당시 울산은 **비가 쏟아진 지 2시간 만에** 하천이 범람했고, 주민 안내가 늦었다는 지적을 받았습니다.
현재 수위만 보면 "아직 경보수위 아래니까 괜찮다"는 판단을 하게 되는데,
시간당 1m씩 오르는 중이라면 40분 뒤엔 경보수위입니다.

그래서 `RiverLevelAnalyzer`는 세 가지를 함께 냅니다.

| 지표 | 의미 |
|---|---|
| 현재 단계 | 관심 / 홍수주의보 / 홍수경보 / 계획홍수위 초과 |
| 상승률 (m/h) | 최근 1시간 관측값의 선형 기울기 |
| **다음 단계 도달 예상시간** | 이것이 실제 대피 리드타임 |

### 상류 → 하류 선행 경고
태화강 사연교(상류)와 태화교(중류)는 통상 1~2시간의 시차가 있습니다.
상류가 급상승하면 중류 도심은 아직 평온해도 **지금 통제를 시작해야** 합니다.
`RiverLevelAnalyzer.upstreamWarning()`이 이 판단을 자동으로 냅니다.

```
상류 태화강(사연교)가 시간당 0.82m로 급상승 중입니다.
통상 1~2시간 후 중류(태화교) 수위 상승으로 이어집니다.
도심 저지대 사전 통제를 지금 시작하세요.
```

4. 하드코딩 정의의 `protectedAreas`, `notes`를 승계해 병합

### 최종 위험도 계산 (v0.3)
```
최종 = (실시간 기본점수 × 지역 취약계수 × 만조계수)
     + 상습침수지 임박 가산
     + 하천 수위 단계 점수 (관심 3 / 주의보 7 / 경보 12 / 계획홍수위 18)
     + 급상승 가산 (시간당 0.5m 이상: +4)
     + 임박 가산 (다음 단계까지 1시간 이내: +3)
     + 과거사례 유사도 가산
```

하천 수위 점수가 가장 큰 이유는, 그게 가장 직접적인 지표이기 때문입니다.
강수량 100mm는 지역에 따라 아무 일 없을 수도 있지만, 계획홍수위 초과는 어디서든 범람입니다.

### 추가 API 키
`local.properties`에 하나 더 필요합니다.
```
FLOOD_SERVICE_KEY=한강홍수통제소_발급키
```

(또는 공공데이터포털 "한강홍수통제소_표준수문DB")

호출 제한은 분당 1,000건 수준이라 3개 지점 10분 폴링은 여유롭습니다.

## 조위 연계 (v0.4)

차바(2016) 당시 울산 피해가 커진 결정적 원인은 **집중호우 시간대가 만조와 겹쳐
빗물이 바다로 빠져나가지 못한 것**이었습니다. 같은 비라도 간조 때 왔으면 피해가 훨씬 작았을 겁니다.
그래서 조위는 참고값이 아니라 위험도 판단의 핵심 변수로 넣었습니다.

### "만조인가"의 이분법으로는 부족하다
세 가지를 함께 봅니다.

| 요소 | 왜 필요한가 |
|---|---|
| 만조 시각 근접도 | 전후 90분 이내면 배수 지연 시작 |
| **만조 조위의 절대 높이** | 대조기(사리) 만조는 소조기보다 훨씬 높다 — 같은 "만조"가 아니다 |
| 배수 차단 임계 초과 | 특정 조위를 넘으면 자연배수가 물리적으로 불가능 |

보정 계수는 이 셋을 합산해 최대 1.5배까지 적용됩니다.

### 하천 수위 × 조위 = 배수 위험
가장 중요한 판단입니다. 하구부에서는 조위가 하천 수위에 근접하면 물이 나갈 곳이 없어집니다.

| 단계 | 조건 | 점수 |
|---|---|---|
| 배수 지연 | 만조 시간대 | +3 |
| 배수 차단 | 조위가 임계 초과, 또는 만조 + 하천 관심수위 | +7 |
| **역류 위험** | 조위 임계 초과 + 하천 홍수주의보 수위 | +12 |

역류 위험 판정 시 알림:
```
만조와 하천 고수위가 겹쳐 역류 위험이 있습니다.
하구 저지대(태화종합시장, 우정동, 태화동, 유곡동) 즉시 통제하고
배수펌프를 최대 가동하세요.
```

### 선제 대응 리드타임
만조가 아직 오지 않았을 때는 남은 시간을 알려줍니다. 이게 실무에서 가장 쓸모 있는 정보입니다.
```
약 137분 후 만조(203cm)입니다.
그 전에 배수 작업을 마치고, 만조 시간대에는 배수 지연을 전제로 대응하세요.
대조기라 만조 조위가 평소보다 높습니다.
```

### API
국립해양조사원(KHOA) 바다누리 해양정보 서비스를 씁니다.
```
TIDE_SERVICE_KEY=국립해양조사원_발급키
```
발급: https://www.khoa.go.kr/oceangrid/khoa/koofs.do (OpenAPI 메뉴)
또는 공공데이터포털 "국립해양조사원_조석예보" (data.go.kr/data/15038991)

사용 엔드포인트:
- `tideObsPreTab` — 조석예보(고조/저조). 하루 단위 고정값이라 **날짜별로 캐싱**해 호출을 아낍니다
- `tideObsRecent` — 실시간 조위 관측
- `ObsServiceObj` — 관측소 목록 (코드 검증용)

### ⚠️ 반드시 검증해야 할 값 두 가지

**1) 울산 조위관측소 코드**
`DT_0063`으로 하드코딩되어 있지만 확실하지 않습니다.
`TideRepository.syncStationCode()`가 앱 최초 실행 시 관측소 목록 API에서 조회해 덮어씁니다.
조위 현황 화면에 "검증되지 않음" 경고가 뜨면 다른 지역 조위를 보고 있는 것이니 꼭 확인하세요.

**2) 배수 차단 임계 조위 (`drainageBlockLevelCm`)**
현재 180cm 임시값입니다. **이 값이 틀리면 배수 위험 판정 전체가 틀립니다.**
정확한 값은 태화강·동천 하구부의 배수문 및 우수토실 표고에서 산출해야 하며,
아래 자료에서 확인 가능합니다.
- 울산시 하수도정비기본계획
- 울산시 자연재해저감 종합계획
- 태화강 하천기본계획

관측소 기준면(DL)과 하천 표고 기준(EL)이 다를 수 있으니 **기준면 환산도 반드시 확인**하세요.
이 부분은 담당 부서에 문의해서 정확한 수치를 받는 것이 가장 빠릅니다.

### 최종 위험도 계산 (v0.4)
```
최종 = (실시간 기본점수 × 지역 취약계수 × 조위계수[최대 1.5])
     + 상습침수지 임박 가산
     + 하천 수위 단계 (관심 3 / 주의보 7 / 경보 12 / 계획홍수위 18)
     + 급상승 가산 (+4) + 임박 가산 (+3)
     + 배수 위험 (지연 3 / 차단 7 / 역류 12)
     + 과거사례 유사도 가산
```

### 전체 API 키 정리
`local.properties`에 네 개가 필요합니다.
```
KMA_SERVICE_KEY=기상청_공공데이터_서비스키
DISASTER_SERVICE_KEY=행안부_안전데이터_서비스키

TIDE_SERVICE_KEY=국립해양조사원_발급키
```

## API 연결 (v0.5)

### 격자좌표 내장
기상청 API는 위경도가 아닌 5km 격자(nx, ny)를 씁니다. 변환 공식(Lambert Conformal Conic)을
`GridConverter.kt`에 구현하고, 울산 12개 지점의 값을 미리 계산해 `UlsanGridPresets`에 넣었습니다.
지역 등록 화면에서 드롭다운으로 고르기만 하면 됩니다.

중구와 남구가 같은 격자(102,84)를 쓰는 건 정상입니다 — 인접해서 같은 격자에 들어갑니다.
강수량 데이터는 같지만 지역 취약도·상습침수지·하천 관측소가 달라 **최종 위험도는 구별로 다릅니다.**

### API 진단 화면
메인 화면 좌하단 `API 진단` 버튼. 5개 항목을 실제로 호출해서 어디서 막히는지 보여줍니다.

- 기상청 특보 / 초단기실황(강수량)
- 행안부 재난문자
- 홍수통제소 하천 수위 (+ 울산 관측소 자동 동기화 결과)
- 해양조사원 조위 (+ 관측소 코드 확정 여부)

각 항목마다 **오류 코드 해석과 해결 방법**을 함께 표시합니다.
기상청 응답코드 30(미등록 키), 20(접근 거부), 22(한도 초과) 등 자주 만나는 오류를 매핑해뒀습니다.

### 설정 순서
`API_설정가이드.md`에 단계별로 정리했습니다. 요약하면:

1. **safetydata.go.kr부터 신청** (승인이 제일 오래 걸림, 최대 3영업일)
2. data.go.kr — 단기예보 + 기상특보
3. hrfco.go.kr — 이메일로 키 발송 (스팸함 확인)
4. khoa.go.kr — 조위
5. `local.properties`에 4개 입력 → Gradle Sync
6. 앱 실행 → API 진단 → 전부 초록색 확인

### Firebase 없이 빌드하려면
`google-services.json`이 없으면 빌드가 실패합니다. 당장 안 쓸 거면
`app/build.gradle`의 google-services 플러그인과 firebase-messaging 의존성,
그리고 Manifest의 `DisasterFcmService` 블록을 주석 처리하세요.
로컬 폴링(15분)만으로도 동작합니다.

## 임계값 검증 (v0.6)

임계값이 맞는지 확인할 방법이 없다는 게 이 앱의 가장 근본적인 문제였습니다.
실제 호우가 와야 검증되는데, 그때는 이미 늦으니까요.

두 가지를 결합해 해결합니다.

### A. 과거 사례 재현 — 극한 구간 담당
차바(2016)와 2025년 7월 호우의 관측값을 시간순으로 넣고 각 시점의 위험도를 계산해,
**실제 피해 발생보다 얼마나 먼저 경보가 떴는지(리드타임)** 를 측정합니다.

| 리드타임 | 판정 | 의미 |
|---|---|---|
| 60분 이상 | 우수 | 주민 대피·통제에 충분 |
| 30~60분 | 보통 | 지하차도 차단, 차량 이동은 가능 |
| 30분 미만 | 경보 지연 | 사실상 사후 통보 |
| 피해 후 | 경보 실패 | 임계값 대폭 하향 필요 |

반대 방향도 봅니다. 2025년 8월 호우(국지 침수만 있었던 경미한 사례)에서
'심각' 단계가 뜨면 **과민 경보**로 판정합니다. 과민 경보가 반복되면
현장에서 알림을 무시하게 되므로 이쪽도 똑같이 위험합니다.

### B. 실측 피드백 — 일상 구간 담당
폴링할 때마다 관측값과 산출된 위험도를 함께 기록합니다(`ObservationLog`).
실제 침수가 발생하면 앱에서 **'피해 보고'** 를 입력하는데,
그러면 그 시점 관측값이 곧 **실제 침수 임계값**으로 남습니다.

```
실측 경보 누락 2건
피해가 보고된 시점에 경보가 발송되지 않았습니다.
해당 시점 최저 시간당 강수량은 32.4mm였습니다.
→ 이 값이 실제 침수 임계값입니다.
  해당 지역 상습침수지의 triggerHourlyRainMm를 32mm 이하로 조정하세요.
```

### 왜 둘 다 필요한가
하나만 쓰면 각각의 약점이 그대로 남습니다.

- **A만** → 3~4건의 보간 추정치에 임계값 전체를 거는 셈
- **B만** → 큰 재해를 한 번도 안 겪은 채로 "경보가 너무 잦다"며 계속 임계값을 올리게 됨

두 번째가 특히 위험합니다. 평온한 몇 달을 근거로 둔감해진 상태에서
차바급이 오는 시나리오죠. 그래서 `ThresholdCalibrator`는 실측 최대 강수량이
극한 사례에 한참 못 미치면 이렇게 경고합니다.

```
극한 구간 미검증
관측 기간 중 최대 시간당 강수량은 28.3mm였습니다.
차바(104.2mm)의 절반에도 못 미칩니다.
→ 실측만으로는 극한 상황의 임계값을 검증할 수 없습니다.
  평온한 기간이 길다고 임계값을 올리지 마세요.
```

### 사용법
메인 화면 `임계값 검증` 버튼 → 과거 재현 결과와 조치 항목이 나옵니다.
시나리오 카드를 탭하면 시간대별 위험도 전개를 볼 수 있습니다.

```
시간  강수(시간당/누적)  위험도
──────────────────────────────────
00:00    5.0/   5.0   3점 주의
01:00   25.0/  25.0   8점 경고
02:00   78.0/  87.0  15점 위험
02:30  104.2/ 139.0  21점 심각
03:00   95.0/ 186.0  24점 심각  ← 실제 피해
        태화강 범람 시작. 태화종합시장·우정동 침수
```

**API 키 없이도 동작합니다.** 지금 바로 확인해 보세요.

## API 장애 대응 (v0.6)

호우 특보가 나면 전국에서 조회가 몰려 공공 API가 느려지거나 실패합니다.
하필 가장 필요한 순간에요.

기존에는 조회에 실패하면 조용히 넘어갔는데, 그러면 사용자는
"아무 일 없음"으로 오해합니다. 그래서 두 가지를 넣었습니다.

1. **마지막 정상값 캐시** (`LastKnownState`) — 실패해도 마지막 확인 시점의 상황을 보관
2. **연속 실패 알림** — 3회 연속(약 45분) 실패하면 명시적으로 알림

```
데이터 수신 중단 — 중구
중구의 기상·재난 데이터를 3회 연속 받지 못했습니다.

마지막 확인 (47분 전):
위험도 12점 · 위험
시간당 강수량 38.0mm

현재 상황은 이보다 나빠졌을 수 있습니다.
기상청·안전디딤돌 앱을 직접 확인하세요.

## 태풍 접근 예측 (v0.7)

### 위험도 점수에 더하지 않았습니다
실시간 위험도는 "지금 침수가 임박했나"(분 단위), 태풍 대비는 "며칠 뒤 뭘 준비하나"(일 단위)입니다.
같은 점수에 합치면 비도 안 오는데 '위험' 단계가 이틀간 떠 있게 되고, 그러면 아무도 안 봅니다.

→ `PreparednessLevel`이라는 **별도 축**을 만들었습니다.
   메인 화면 상단 배너로 표시되며, 대비 단계 이상일 때만 나타납니다.

| 단계 | 조건 |
|---|---|
| 관찰 | 실효거리 400km 이내, 진로 변동 큼 |
| 대비 | 강풍반경 진입 또는 실효거리 200km 이내 |
| 비상 준비 | 폭풍반경 진입 또는 만조 완전 중첩 |
| 임박 | 24시간 내 최근접 |

### 거리보다 통과 방향
북반구 태풍은 진행방향 오른쪽이 위험반원입니다.
태풍이 **울산 서쪽**으로 지나가면 울산이 위험반원에 들어가 같은 거리라도 영향이 훨씬 큽니다.
차바가 이 경우였습니다.

`PassageSide`에 방향별 가중치를 두고, 실효거리 = 실제거리 ÷ 가중치로 계산합니다.

| 통과 방향 | 가중치 |
|---|---|
| 직상 통과 | 1.5 |
| 서쪽 통과 (위험반원) | 1.4 |
| 동쪽 해상 (가항반원) | 0.85 |

### 핵심 기능: 만조 겹침 예측
이 모듈에서 가장 값어치 있는 산출물입니다.

태풍 예보는 **3일 전**에 나오고, 조석은 **몇 달 뒤까지** 계산됩니다.
두 개를 맞춰보면 차바형 복합재해 조건을 사흘 전에 알 수 있습니다.

```
⚠ 최근접 시각과 만조가 완전히 겹칩니다.
  만조 10월 5일 10시 47분, 조위 218cm (대조기).
  빗물이 바다로 빠지지 못해 태화강·동천 하구가 역류할 수 있습니다.
  차바 당시 울산 피해가 커진 것이 정확히 이 조건이었습니다.
  만조 전에 사전 배수를 마치고, 배수펌프와 이동식 펌프를 미리 배치하세요.
```

| 판정 | 조건 |
|---|---|
| 완전 중첩 | 90분 이내 + 대조기 |
| 겹침 | 90분 이내 |
| 근접 | 3시간 이내 |

### 불확실성을 숨기지 않습니다
3일 전 진로 예보는 오차가 큽니다. "온다/안 온다"로 단정하면 빗나갔을 때 신뢰를 잃습니다.

- 예보원 반경을 그대로 표시하고, **최소 가능 거리**를 함께 계산합니다
- 신뢰도(낮음/보통/높음)를 명시합니다
- 이례적 경로일 때는 위험반원 판정을 **유보**합니다 (`PassageSide.UNKNOWN`)

### 알림 채널 분리
태풍 대비 알림은 일반 채널로 보냅니다. 며칠 전부터 뜨는 정보를 긴급 채널로 보내면
정작 침수 임박 알림이 묻히기 때문입니다.
단, 24시간 내 최근접이거나 만조 완전 중첩이면 긴급 채널로 격상합니다.

### API 추가 신청 필요
`data.go.kr`에서 **"기상청_태풍정보 조회서비스"** 를 추가 활용신청하세요.
인증키는 기존 `KMA_SERVICE_KEY`와 동일한 것을 씁니다.

⚠️ 태풍정보 API는 버전에 따라 응답 필드명이 달라진 이력이 있습니다.
`TyphoonApiService.kt`의 필드명을 발급받은 명세서와 반드시 대조하세요.

### 웹 검증 도구에도 추가
`검증도구.html`에 만조 겹침 계산기를 넣었습니다.
태풍 최근접 시각과 만조 시각만 넣으면 판정이 나옵니다. API 키 없이 동작합니다.

## 태풍 API를 API허브로 교체 (v0.9)

실제 발급 화면 확인 결과, 태풍정보는 **data.go.kr이 아니라 기상청 API허브**에 있었습니다.
두 시스템은 인증 방식부터 응답 형식까지 전부 다릅니다.

| 항목 | data.go.kr | apihub.kma.go.kr |
|---|---|---|
| 인증 파라미터 | `serviceKey` | **`authKey`** |
| 응답 형식 | JSON/XML | **평문 텍스트** |
| 엔드포인트 | .../getTyphoonInfo | `api/typ01/url/typ_now.php` |
| 키 | KMA_SERVICE_KEY | **KMA_APIHUB_KEY (별도)** |

→ 키가 하나 늘어 **총 5개**가 되었습니다.

### 텍스트 파서를 새로 만들었습니다
JSON이 아니라 콤마 구분 평문이라 Gson을 쓸 수 없습니다.

**컬럼 순서를 가정하지 않는 구조로 짰습니다.** `help=1`로 변수명 헤더를 함께 받아
이름→인덱스 맵을 만든 뒤 이름으로 값을 꺼냅니다. 기상청이 컬럼을 추가하거나
순서를 바꿔도 깨지지 않습니다.

호출 파라미터와 선택 근거:

| 파라미터 | 값 | 이유 |
|---|---|---|
| `disp` | 1 | 콤마 구분. 0(고정폭)은 컬럼 폭 변경에 취약 |
| `help` | 1 | 변수명 헤더 포함 → 순서 무관 파싱 |
| `mode` | 2 | 최근 분석정보 + 예측정보를 함께 |

### 필드 매핑

| API허브 | 앱 | 비고 |
|---|---|---|
| LAT / LON | 위경도 | |
| PS | 중심기압 | |
| WS | 최대풍속 | 강도(약~초강력) 자동 분류 |
| RAD15 | 강풍반경 | 크기(소형~초대형) 자동 분류 |
| RAD25 | 폭풍반경 | |
| **RAD** | **예보원 반경** | 70% 이상 예상확률반경 — 진로 불확실성 |
| TYP_TM / FT_TM | 분석시각 / 예측시각 | **UTC** 기준이라 변환 필요 |

`RAD`(70% 확률반경)를 예보원 반경으로 씁니다. 이 값이 클수록 진로가 불확실하다는 뜻이라
신뢰도 판정에 그대로 쓰입니다.

### 주의할 점
- **시각이 UTC입니다.** KST로 변환하지 않으면 만조 겹침 판정이 9시간 어긋납니다.
  파서에서 `TimeZone.getTimeZone("UTC")`로 처리했습니다
- typ_now는 **태풍명(한글)을 주지 않습니다.** 번호만 옵니다.
  이름이 필요하면 `typ_list.php`를 별도 호출해야 합니다
- 결측값은 `-9`, `-99`, `-999` 등으로 옵니다. 파서에서 null 처리했습니다

## 강수량 소스를 AWS 실측으로 교체 (v1.0)

### 왜 바꿨나
기존에는 data.go.kr 초단기실황(5km 격자)을 썼습니다. 이건 **보간값**이라
국지적 극값이 평활화됩니다.

차바 당시 울산 관측소 시간당 최대는 104.2mm였지만, 북구 매곡동은 **124mm**였습니다.
그리고 피해는 매곡동에서 났습니다. 격자값으로는 이런 지점 극값을 놓칩니다.

| | 초단기실황 (data.go.kr) | **AWS (API허브)** |
|---|---|---|
| 단위 | 5km 격자 보간 | **실제 관측소 지점값** |
| 울산 | 격자 3~4개 | 관측소 9곳 이상 |
| 갱신 | 1시간 | 매분~10분 |

### 평균이 아니라 최댓값을 씁니다
지역 내 여러 관측소 중 **최댓값**을 위험도 계산에 넣습니다.
평균을 쓰면 국지 호우가 희석되는데, 피해는 최댓값 지점에서 나기 때문입니다.

지점 간 편차가 크면 "국지성 호우"로 판정하고 경고합니다.
```
시간당 최대 87.0mm (매곡) · 지역 평균 31.2mm
국지성 호우 — 지점 간 편차가 큽니다. 평균값으로 판단하지 마세요.
```

### 폴백 구조
```
AWS (awsh.php)  실패 →  종관관측 (kma_sfctm2.php)  실패 →  초단기실황 (data.go.kr)
```
세 단계로 내려가므로 하나가 막혀도 강수량 판단이 멈추지 않습니다.

### ⚠️ 반드시 검증할 것: 울산 AWS 지점번호
`UlsanAwsStations`의 지점번호는 **확정되지 않은 값**입니다.
이게 틀리면 울산 관측소가 하나도 매칭되지 않아 초단기실황으로 폴백됩니다.

진단 화면이 이 상황을 잡아냅니다.
```
○ 기상청 API허브 · AWS 실황
전국 512개 지점 수신, 그러나 울산 지점이 매칭되지 않음
수신된 지점번호 예시: 90, 93, 95, 98, 99, 100, ...
→ API허브 '지상관측 > 지점정보'에서 울산 지점번호를 확인해 교체하세요.
```

### 시각 기준이 API마다 다릅니다 (주의)
| API | 기준 |
|---|---|
| 태풍정보 (typ_now) | **UTC** |
| 지상관측 (AWS/ASOS) | **KST** |

같은 API허브인데 다릅니다. 파서에서 각각 명시 처리했습니다.
섞이면 만조 겹침 판정이 9시간 어긋납니다.

### 단기예보는 쓰지 않습니다
API허브에 단기예보도 있지만 이건 **예보**입니다.
위험도는 "지금 얼마나 왔나"(실황)로 계산해야 하므로 쓰지 않습니다.
(태풍 대비 단계에서만 예측값을 쓰고, 그것도 위험도 점수와 분리되어 있습니다)

## 조석예보 API 교체 (v1.1)

khoa.go.kr 직접 호출에서 **data.go.kr 경유**로 바꿨습니다.

| 항목 | 이전(khoa) | 현재(data.go.kr) |
|---|---|---|
| End Point | khoa.go.kr/api/oceangrid/ | `apis.data.go.kr/1192136/tideFcstHghLw` |
| 상세기능 | tideObsPreTab | `GetTideFcstHghLwApiService` |
| 응답 구조 | result/data | 포털 표준 response/header/body/items |
| 일일 트래픽 | - | 10,000건 |

`TIDE_SERVICE_KEY`는 **`KMA_SERVICE_KEY`와 같은 값**입니다 (둘 다 data.go.kr).

### 실시간 조위 관측이 없습니다 — 보간으로 해결
이 API는 **고조·저조 예보만** 줍니다. 실시간 관측값이 없습니다.

인접한 고조·저조 사이를 **코사인 보간**해 현재 조위를 추정합니다.
조석은 사인 곡선에 가깝게 변하므로 선형 보간보다 실제에 훨씬 가깝습니다.
극값 부근에서 완만하고 중간에서 가파른 실제 조석 곡선을 재현합니다.

### 폭풍해일 보정을 넣었습니다 (중요)
조석예보는 **천문조**입니다. 태풍이 접근하면 실제 해수면은 이보다 높아집니다.
- 기압 저하: 1hPa당 약 1cm 상승
- 취송류: 바람이 해수를 해안으로 밀어올림

차바 당시에도 그랬습니다. 예보만 믿으면 **실제보다 낮게 판단**하게 되고,
그건 안전측이 아닙니다.

→ 태풍 영향권(대비 단계 이상)일 때 조위에 **+50cm** 여유를 더해 판단합니다.
   `TideRepository.STORM_SURGE_MARGIN_CM`에서 조정할 수 있습니다.

```
태풍 영향권 → 조위 추정 190cm + 폭풍해일 여유 50cm = 240cm
→ 배수 차단 임계(180cm) 초과 판정
```

### ⚠️ 울산 관측소 코드 확인 필요
`DT_0063`으로 두었으나 확정되지 않았습니다.
이 API에는 관측소 목록 조회가 없어 자동 검증이 불가능합니다.

**다운받으신 활용가이드 hwp의 관측소 코드표**에서 울산을 찾아 확인하세요.
진단 화면이 "응답은 정상이나 데이터가 없습니다"로 나오면 코드가 틀린 것입니다.

이 값이 틀리면 만조 겹침 판정이 전부 무의미해집니다.

인접 지점(울산152·매곡943)으로 대체하되, 중구 판단은 다른 구보다
불확실성이 크다는 점을 명시했습니다. (`hasOwnStation()`으로 구분)

### 품질검사 플래그 반영
AWS 자료는 관측값 정상 여부를 플래그로 제공합니다.
**0=정상, 1=오류, 9=결측**

오류값을 안 거르면 장비 이상으로 튄 값이 그대로 위험도에 들어갑니다.
저희는 **최댓값**을 쓰기 때문에 이상값 하나가 곧바로 오경보가 됩니다.

2중으로 막았습니다.
1. QC 플래그가 0이 아니면 제외
2. 플래그가 없을 때를 대비해 **물리적 상한 180mm/h** 적용
   (국내 관측 사상 최대 시간강수량 약 145mm 기준)

제외된 지점 수는 화면에 표시합니다.
```
시간당 최대 87.0mm (매곡) · 지역 평균 31.2mm
국지성 호우 — 지점 간 편차가 큽니다.
※ 1개 지점은 관측값 오류·결측으로 제외했습니다.
```

## 울산시 공식 통제·대피 기준 반영 (v1.4)

**2026년 여름철 자연재난 대비 재난상황 대응계획서**의 하천재해 기준을 반영했습니다.

### 앱 점수와 섞지 않았습니다
앱의 위험도는 여러 변수를 가중합산한 **추정치**이고,
대응계획서 기준은 시가 정한 **공식 기준**입니다.

한 점수로 섞으면 앱이 공식 기준을 덮어쓰는 모양이 됩니다.
현장에서 앱과 매뉴얼이 다른 말을 하면 뭘 따라야 할지 혼선이 생기고,
책임 소재도 불분명해집니다.

→ 알림과 화면에서 **위아래로 나눠** 표시합니다.
```
■ 울산시 대응계획서 기준
  대피③ 하천제방 만수위 90% 도달
     → 현재 94% (7.5m / 8.0m)
  · 통제에 더해 대피 조치를 시행하세요

■ 앱 참고 판단 (위험도 38점 · 심각)
  ...
```

앱의 역할은 판단을 대신하는 것이 아니라,
**이미 정해진 기준에 도달했음을 먼저 알려주는 것**입니다.

### 반영한 기준

**통제**
| 조항 | 기준 |
|---|---|
| 통제① | 누적강우 200mm 이상 관측 |
| 통제② | 시간당 최고 30mm 예보 시 |

**대피**
| 조항 | 기준 |
|---|---|
| 대피① | 누적강우 250mm 이상 관측 |
| 대피② | 시간당 30mm 이상 & 3시간 90mm 강수 예상 |
| 대피③ | **하천제방 만수위 90% 또는 교량 수위 90% 도달** |
| 대피④ | 홍수경보 발령 시 |
| 대피⑤ | 호우 상황에서 댐 방류 협의 시 |

통제 범위는 침수심 **최소 15cm** 영향 범위입니다.

### 대피③이 계획홍수위 문제를 부분적으로 해결합니다
"제방 만수위 90%"는 **비율 기준**이라, 계획홍수위 절대값이 정확하지 않아도
비율로는 판정이 가능합니다. 다만 만수위 값 자체가 임시값(8.0m)이면
90% 지점도 함께 어긋나므로, 하천기본계획 확인은 여전히 필요합니다.

### 근거를 함께 표시합니다
어떤 조항에 걸렸는지, 실제 관측값이 얼마인지 함께 보여줍니다.
현장에서 "왜 이 알림이 왔는지" 즉시 확인할 수 있어야 신뢰할 수 있기 때문입니다.

### 대피 기준 도달은 무조건 긴급 채널
앱 자체 위험도가 낮게 나와도, 공식 대피 기준에 걸리면 긴급 알림으로 나갑니다.

같은 비라도 어디가 위험해지는지가 완전히 달라서, 하나로 뭉뚱그리면 놓칩니다.

### 지하공간이 가장 빠릅니다 — 15분 단위
| 구분 | 기준 |
|---|---|
| 통제① | 15분 20mm 이상 & 1시간 이상 지속 예상 |
| 통제② | 침수심 5cm 도달 예상 |
| 대피① | 15분 30mm 강우 지속 |
| 대피② | 시간당 55mm 강우 예상 |

**시간당으로만 보면 지하차도 익사를 놓칩니다.** 15분에 30mm가 쏟아져도
시간당으로는 아직 낮게 보이기 때문입니다.

대피 원칙도 다릅니다 — "일시에 물이 차오르는 특성을 감안, **즉시대피**".
하천·산사태는 사전대피가 원칙인데 지하공간만 즉시대피입니다.

### 산사태는 연속강우가 필수 조건
| 구분 | 기준 |
|---|---|
| 통제① | 누적 200mm **&** 연속 100mm 이상 관측 |
| 통제② | 시간당 최고 20mm 또는 일강우 100mm 예보 |
| 대피① | 누적 250mm **&** 연속 100mm 이상 관측 |
| 대피② | 시간당 50mm 또는 일강우 200mm 예상 |
| 대피③ | **취약시간(일몰 후~일출 전) 시간당 최고 30mm 예상** |

`&` 조건이라 단기 폭우만으로는 발령되지 않습니다.
이걸 `또는`으로 잘못 넣으면 산사태 경보가 과다 발령됩니다.

**대피③이 특징적입니다.** 야간에는 같은 30mm라도 대피 기준입니다.
"주로 거주지와 취약시간(새벽~오전)에 발생"하는 특성 때문입니다.
앱은 19시~07시를 취약시간으로 판정합니다.

### 유형별로 나눠 알립니다
```
[대피] 중구 · 지하공간 침수·하천재해

■ 울산시 대응계획서 기준

🕳 지하공간 침수 — 대피
  대피① 15분 30mm 강우 지속 시
     → 15분 34mm

🌊 하천재해 — 통제
  통제② 시간당 최고 30mm 예보 시
     → 시간당 42mm

· [지하공간] 일시에 물이 차오르는 특성 감안, 즉시대피 원칙
· [지하공간] 긴급재난문자 발송 및 주민대피 명령(민방위 사이렌)
· [하천] 침수심 15cm 이상 영향 범위 사전통제

■ 앱 참고 판단 (위험도 21점 · 심각)
```

### ⚠️ 15분 강수량이 아직 근사값입니다
지하공간 기준의 핵심인데, 현재는 **시간당÷4**로 근사하고 있습니다.

집중호우는 고르게 오지 않습니다. 시간당 60mm가 앞 15분에 40mm 몰렸다면
실제로는 대피 기준인데 근사값으로는 15mm로 계산되어 **놓칩니다.**

→ AWS **매분자료** 연계가 필요합니다. API허브 지상관측 메뉴에
분 단위 자료가 있는지 확인이 필요합니다.

```
`cgi-bin`이 들어갑니다. 다른 API허브 경로와 형태가 다릅니다.

| 파라미터 | 설명 |
|---|---|
| tm1 / tm2 | 시작·종료 시각 yyyyMMddHHmm (KST) |
| stn | 지점번호 (0이면 전체) |

**조회 기간 제한이 있습니다.**
- 전체지점(stn=0): 10분 이내
- 단일 지점: 하루 이내

15분 구간을 받으려면 **지점을 지정해야** 합니다.
그래서 강수량이 가장 많은 지점(최댓값 원칙)을 골라 조회합니다.

### 관측 지연 고려
자료가 실시간보다 약간 늦게 올라오므로 **2분 여유**를 두고 조회합니다.
여유 없이 현재 시각으로 조회하면 마지막 몇 분이 비어 과소평가됩니다.

### 폴백은 유지합니다
매분자료 조회에 실패하면 시간당÷4 근사로 돌아가되,
**관측값 문구에 "(시간당에서 근사)"를 명시**합니다.
근사값인지 실측인지 구분되지 않으면 판단을 그르칩니다.

## 지하차도 침수센서 연계 불가 — 공백을 메우는 방식 (v1.9)

센서는 설치되어 있으나 **현장 차단기 전용이라 외부 시스템으로 값이 나오지 않습니다.**
연계 경로가 없는 것으로 확인되었습니다.

### 영향
| 관할 | 지점 |
|---|---|
| 중구 | 6개소 (동천·우정·학성강북·번영교강북·명정 지하차도, 성남·우정 지하보도) |
| 남구 | 5개소 (학성교강남·삼호·삼산·번영교강남·명촌강남 지하차도) |

**가장 위험한 지점이 전부 자동 판정 불가**입니다.
지하차도는 물이 차오르면 몇 분 안에 갇히는 곳이라, 이 공백은 그냥 두면 안 됩니다.

### 침묵하지 않기로 했습니다
가장 위험한 실패는 앱이 조용히 있어서 사용자가 **"이상 없음"으로 오해**하는 것입니다.

그래서 강수량이 일정 수준을 넘으면 **판정 대신 현장 확인을 요청**합니다.

```
[확인요망] 중구 · 지하차도 6개소

■ 현장 확인 필요 (6개소)
  침수심 센서가 연계되지 않아 자동 판정이 불가합니다.
  · 동천지하차도 (남외동 690-4)
  · 우정지하차도 (성남동 316-3)
  ...
  → CCTV 또는 현장 순찰로 직접 확인하세요
```

**판정이 아니라 환기입니다.** 앱이 "통제하라"고 말하지 않고
"이 지점을 지금 확인하라"고만 말합니다. 근거 없는 판단을 내리는 것보다
모른다는 사실을 정확히 알리는 쪽이 안전합니다.

### 발동 기준
시간당 20mm 또는 15분 10mm 또는 50mm/h 지속.
대응계획서 통제기준의 하한선 언저리로, 지하공간 침수가 시작될 수 있는 수준입니다.

통제 대상이 하나도 없어도 이 알림은 따로 나갑니다.
화면에서도 **빨간색으로 별도 섹션**에 표시하며,
"앱은 이 지점들을 '이상 없음'으로 판단하지 않습니다"를 명시합니다.

## 지하차도 전수 목록 반영 — 30개소 (v2.0)

대응계획서 별첨의 **지하차도 관리현황**을 반영했습니다.

### 제가 세던 방식이 틀렸습니다
이전에는 통제지점 목록(ControlSites)에 실린 지하차도만 셌습니다.
그런데 **실제 지하차도는 30개소**이고, 통제지점에는 일부만 실려 있었습니다.

통제지점에 실린 것만 보여주면 **나머지가 사각지대로 남습니다.**
침수 위험은 통제지점 지정 여부와 무관하게 모든 지하차도에 있습니다.

### 위험등급이 이미 매겨져 있었습니다
| 등급 | 개소 |
|---|---|
| **고위험** | **17** |
| 저위험 | 13 |

인력이 제한된 상황에서 **순찰 우선순위**를 정하는 근거가 됩니다.
알림에서 고위험을 앞에 배치합니다.

### 관리기관
대부분 **종합건설본부** 소관입니다.
센서 연계를 나중에 다시 타진한다면 이곳이 1순위 창구입니다.

| 기관 | 개소 |
|---|---|
| 종합건설본부 | 22 |
| 울주군 도로과 | 4 |
| 시 건설도로과 (울산하버브릿지) | 2 |
| 중구 건설과 | 1 |
| 남구 건설과 | 1 |

### 알림이 이렇게 나갑니다
```
[확인요망] 중구 · 지하차도 7개소

■ 지하차도 확인 필요 (7개소)
  침수심 센서가 외부 연계되지 않아 자동 판정이 불가합니다.

  [고위험 5개소 — 우선 확인]
  · 우정지하차도
  · 번영교강북지하차도
  · 학성교강북지하차도
  · 동천지하차도
  · 명정지하차도
  [저위험 2개소]

  → CCTV 또는 현장 순찰로 직접 확인하세요
```

통제지점에 지정되지 않은 지하차도는 화면에 **"공식 통제기준 미지정 — 판단 근거가 더 부족합니다"**
를 함께 표시합니다. 기준이 없다는 것은 안전하다는 뜻이 아니라, 판단할 근거가 없다는 뜻입니다.

## 지하차도 4단계 기준 — 센서 없이도 판정 가능 (v2.1)

대응계획서에 **지하차도 전용 4단계 기준**이 따로 있었습니다.
심각 단계를 뺀 나머지는 **전부 강수량·특보로 판정됩니다.**

침수심 센서 연계가 불가능해 판정을 포기했던 영역인데, 상당 부분 되살아났습니다.

| 단계 | 기준 |
|---|---|
| **관심** | 강우량 30mm/일 이상 예보 · 예비특보 발효 |
| **주의** | 호우주의보 · 3시간 60mm · 12시간 110mm · 태풍주의보 |
| **경계** | 호우경보 · 3시간 90mm · 12시간 180mm · 홍수주의보 |
| **심각** | 대규모 재난 가능성 확실 · 홍수경보 · **침수심 5cm** |

→ **경계까지 자동, 심각만 현장 확인**

### 단계별 조치사항도 그대로 담았습니다
```
■ 지하차도 경계 단계
  호우경보 → 호우경보 발효 중
  3시간 90mm 이상 → 3시간 96mm

  [조치사항]
  · 현장담당자 실시간 상황보고 및 통제준비
  · 유관기관 지원요청
  · 차단시설 가동 준비

  [침수우려 높음 17개소 — 4인 배치 대상]
  · 우정지하차도
  · 명정지하차도
  ...

  ※ 침수심은 센서 미연계로 확인 불가 — 심각 단계 판정은 현장 확인 필요
```

### 즉시 통제 사유는 단계와 별개입니다
아래 중 하나라도 해당하면 단계와 무관하게 즉시 통제입니다.

- 배수펌프 미작동·처리용량 초과로 지하차도 내 물이 고이거나 증가
- 홍수통제소·하천관리청 등으로부터 하천범람 우려 통보
- **경찰·기상청 등 관계기관으로부터 통제 필요 통보**
- 도로관리청 판단 (최대 침수심 5cm)

세 번째 항목은 **경찰이 통제를 요청하는 경로**를 명시한 조항입니다.
이 앱을 경찰 쪽에서 쓴다면 직접적인 근거가 됩니다.

### 침수우려 높은 지하차도 17개소
4인 배치 대상(도로관리기관·읍면동·이통장/방재단·**경찰**)이며,
별첨 목록의 **고위험 17개소와 정확히 일치**합니다.

일반 지하차도는 2인 이상입니다.

### 외수침수 우려 5개소 — 하천 수위로 선제 판단 가능
내수침수(자체 배수 불량)와 달리 **하천 범람**이 원인인 곳들입니다.
하천 수위 데이터로 미리 잡을 수 있습니다.

| 지하차도 | 연계 하천 |
|---|---|
| 명촌강남 | 태화강 |
| 명촌본선 | 태화강 |
| 상방 | 명촌천 |
| 울산역 | 태화강 |
| 신화 | 작괘천 |

※ 신화지하차도는 작괘천 제방보다 지반고가 높아 위험이 낮음 (대응계획서 각주)
